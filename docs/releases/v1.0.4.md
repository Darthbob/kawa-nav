Nine fixes found in an audit of the app, in three areas: what a release build may do from outside, what could lose a ride, and what the dash shows. How KawaNav talks to the bike is unchanged from 1.0.3.

### Fixed

- **A release build no longer acts on the extras a start intent can carry.** KawaNav's screen has to be startable by any app on the phone (Android requires it for the launcher), and it was reading control extras a debug build uses — with them, an installed app could start an offline-region download on mobile data, cancel one, export the log or stop the bridge. Every one of them now goes through one gate that refuses them unless the build is a debug one. Nothing else about the app can be driven from outside.
- **Revoking "Nearby devices" no longer crashes the automatic start.** The user can revoke the Bluetooth permission while the companion-device association stays; Android then still tells KawaNav the bike is there, but every Bluetooth call throws, on the main thread, so the bike appeared and the bridge crashed instead of starting, with nothing said. The background paths now ask before they start, the remaining calls are guarded, and the app says what is missing and what to do.
- **A ride can no longer be lost while it is compressed.** A finished ride was gzipped in place and the plain file deleted before the compression's trailer was written: an app killed (or a full disk) halfway left a half-written `.tsv.gz`, which is the file a reader prefers, so the ride was unreadable for good. The gzip now goes to a temporary name and is renamed into place only when it is whole; the plain file is deleted after that; and a ride left half-compressed by the older version is read from its plain file instead of showing as empty.
- **Offline maps of the individual US states download again.** Their Geofabrik names contain a "/" (`us/alabama`), which was used to build a file path: the directory does not exist, so the download failed before the first byte, and the region would not have been found again in the list either. The "/" is folded into "_" for the files on the phone; the region keeps the name Geofabrik gave it.
- **A ride with no GPS fix says so while it runs.** After a background start in an area where KawaNav could not ask for the location yet, the ride got no track at all and the rider learned it only from the ride list afterwards. Home now shows "no GPS track" beside the distance and time, and KawaNav asks for the location again as soon as the app is opened or the ride is continued — the track then starts from that point.
- **Turns are read correctly again.** The instruction text was matched too loosely: a street name changed the arrow ("Continue on Rampart Street" became a ramp, "Emergent Avenue" a merge, "Auffahrtsallee" an on-ramp), and a roundabout exit was taken from an ordinal anywhere in the text, so a place name ("Prima Straße, dann Kreisverkehr") could choose the exit. The words are now anchored where the language allows and checked against their inflections, the exit number is read in the clause that names the maneuver, and a text that names only the kind of maneuver leaves Maps' arrow alone instead of overriding the side it drew. A roundabout whose arrow Maps drew *and* whose number the text names keeps the arrow's direction and takes only the number; the traffic-side setting is not consulted there.
- **Half a Bluetooth packet is ignored instead of shown.** A live frame the meter sends cut short — the link may fall back to the smallest packet size — was decoded past its end, where every byte reads as −1: it showed a lean of about −100.2°, an absurd acceleration and a gear of 15 for a second. A frame shorter than the length in its own header is now dropped whole.
- **Turning KawaNav off clears the dash.** The "clear" and "icons off" frames were written and the link closed on a fixed half-second delay, but they were still queued (a write may take up to three seconds) and closing the link empties the queue: the last arrow and the status icons stayed on the meter. The link is now closed when the writes are done, with a timeout just above the write timeout as a backstop.
- **A call or message that arrives while KawaNav is down is no longer lost.** The dash icons were sent only when the notification changed, so one posted while the bridge was stopped was never shown. Both icons are now brought in line with the phone on every connection.

### Also fixed in this version

Found in a second pass over the same audit: smaller, but three of them lose data or take the app down.

- **A ride that is being recorded can no longer be deleted by mistake.** The ride in progress shows up in the ride list from its first summary save, and nothing marked it. Opening it and deleting it unlinked the file the recorder was still writing into: every later sample went nowhere, and at Stop the ride came back as a finished ride with no track at all (the delete ran on a second store, so the recorder never noticed). The open ride is now kept by the process rather than by one store, the list marks its row "· recording now", and both the list and the ride screen refuse the delete until the ride is stopped.
- **A ride whose track does not come back says so.** When the app is killed mid-ride, the summary in the JSON is only as fresh as the last periodic save, so the samples decide what the ride is — and when they cannot be read (the `.tsv.gz` truncated or gone) the sample count was overwritten with 0 while the distance and the time kept their real values: the ride read like one that recorded nothing. Such a ride now keeps the summary's own count and is listed as "· track lost" instead of "· recovered after a restart".
- **An offline download Android stops no longer takes the app down.** A `dataSync` foreground service may only run six hours per day on Android 15+; the system then calls `Service.onTimeout`, and an app that does not stop itself within a few seconds gets a fatal exception. A multi-gigabyte region over mobile data can reach that. The service now handles the timeout, says in the notification that Android stopped it, and can be started again. Cancel was also only read by the download loop and not by the region-list and file-size steps, so it could sit on "Cancel" while the download kept going; every step now sees it.
- **The log's 2 MB cap cannot stop working in silence.** Rotating deleted the previous `kawanav.log.1` first and then renamed the full log over it, ignoring whether the rename worked: a failed rename threw the backup away, left the full file in place and kept appending to it, so the cap never took effect again. It is now a single move that either happens or does not, and the log-writing path cannot die on an exception without a word.
- **The Home and Settings screens no longer call the companion-device service twice a second.** Both refresh every 500 ms, and each refresh asked the system for the bike's association — a binder round-trip plus a name lookup, on the main thread, for as long as either screen is in front. It is now cached and re-read when it can change (pairing, autostart off, the system callbacks, and coming back from the system's Bluetooth settings). The other system checks on the same refresh (permission, Bluetooth on, battery optimisation) are made once every four seconds instead of every half second.
- **Pairing that cannot start leaves nothing behind.** If `createBond` refused (ignition off, for instance) no state change ever arrives, so the bond-state receiver stayed registered for the life of the process and every later pairing added another one. It is now dropped on that path and replaced before a new attempt.
- **The first-start guide cannot skip a permission for good.** The guide saved the *next* step before running the current one, so an app killed while a permission dialog was on screen marked that step done and never asked again. It now saves the step in progress: a permission granted meanwhile is skipped, one that was never asked comes back.

Also in this pass: `IconMemory`'s hand-taught icon store was removed — nothing ever wrote it, so the branch could never be taken.

### Not yet tried on a bike

Every fix above is covered by unit tests (232 in the app; `RideStoreRecoveryTest` and `LoggerRotationTest` are new, and `RideStoreCompactTest` gained the two delete cases), but none of it has been on a ride yet. Worth checking when you can: with the bike off, let a call come in and then start KawaNav — the icon should appear; switch the bike off while an arrow is on the dash — the arrow and the battery icon should go out; download one `us/*` region end to end and find it again in the list. A report should include Settings → "Export the log and the capture" and what you saw on the dash. Unchanged from 1.0.3: the values and warnings, what the two traction-control pairs report, which rotation rate is which axis ([docs/PROTOCOL.md](https://github.com/Darthbob/kawa-nav/blob/v1.0.4/docs/PROTOCOL.md)), the dashboard's capability answer, writing riding modes 5-7 in the debug build and the byte 88 wheel-speed setting.
