The ride file now keeps everything the bike sends while riding — suspension, the body's movement, torques, brake pressures — and the app obeys what the dash says it can do. A census of every parameter Rideology reads or writes closed the last gaps: about 1,250 fields over 54 frame ids were compared with KawaNav and written down in [docs/PROTOCOL.md](https://github.com/jackyes/kawa-nav/blob/v0.8/docs/PROTOCOL.md).

### New
- **The ride records the whole bike.** Until now the suspension and IMU frame (0x4B) was decoded and shown live but never written down. A ride now keeps, per second: front and rear suspension travel and their speeds, the three accelerations, the three rotation rates, the filtered front and rear wheel speeds, the suspension unit's traction-control levels and quick-shifter flags, plus the rest of the live frame (torque asked and given, brake pressures, ABS target and indicator, damping, cruise control, wheelie angle). All of it appears in the GPX export; the suspension travel, the three accelerations and the two filtered wheel speeds are chartable (the chart list offers them for the rides that have them), and anything the bike does not report stays an empty cell — in the CSV too, rather than the `-1` a 0.7 ride wrote.
- **Up to seven riding modes.** On a bike whose tuning configuration announces four rider modes, the settings screen now offers Rider 2, 3 and 4 as well (Rideology does the same). The list follows the bike: four entries on a bike with four modes, seven where the bike says so. Writing them stays in the debug build until it has been tried standing still on a real bike.

### Changed
- **The dash's own answer is obeyed.** If its capability frame says it shows no status icons, the icon frame is not sent; if it says it has no turn-by-turn, the arrow frames are not sent — the behaviour Rideology has. Nothing changes when the frame has not arrived or is still being prepared: KawaNav keeps sending, because a missing answer is not a "no". **Settings → "Send arrows and icons anyway"** turns the obeying off for a dash that answers wrongly (arrows and icons worked before, now missing): this is a normal setting, not a debug one, so a release build always has a way back. The log, and the hint on the Home screen, say when something is being held back.
- **Byte 88 of the live frame is not a cruise speed.** Rideology calls it the wheel-speed setting and stores it as a plain calibration number; it is now shown raw on the debug card instead of being read as a cruise speed.
- **The 0x47 tuning config is asked for again** when the meter answers "not ready", like the other configuration frames.
- **A ride continued after this update keeps its old column set** (the file a 0.7 build started has fewer columns than today's): the new values are missing from that one ride rather than the file turning ragged.
- **What is not there is written as nothing.** A value the bike did not send is an empty cell in the ride file instead of a `-1`, so charts and the ABS/traction-control marks no longer read "no value" as an event.
- The protocol document gained a full table of the 0x40 configuration nibbles (which value each 2-bit field enables, and which frame reads it), the valid-bit bytes of the 0x41 and 0x45 frames, the long form of 0x45 (a second copy of the dash's own numbers, which the Z900 does not send), the exact conditions under which the icon and arrow frames are dropped, the corrected retry rule, and a frame-id inventory marking what belongs to the EV/HEV bikes and to the older BLE4 dashes.

### Fixed
- The wheelie flag, torque, brake pressures and the ABS state were shown live but never recorded; they are in the file now.
- The rotation rates, the accelerations and the suspension travel of a ride are exportable instead of being lost when the ignition goes off.

### Not yet tried on a bike
- **What the ride file's new values mean.** The suspension travel, the accelerations and the rotation rates are decoded exactly as Rideology decodes them, but nobody has compared them with the dash while riding: the unit of the travel, which axis is which, and whether the numbers agree are all open. The same goes for the torque, brake and ABS values the 0.7 release added.
- **The capability answer.** No capture from a real Z900 of the 0x1A frame exists yet, so the app keeps sending whenever that answer is missing or unready, and says in the log (and on the Home screen) when it holds something back. If a dash that does show arrows reports "no turn-by-turn", **Settings → "Send arrows and icons anyway"** restores the old behaviour — check this on the first ride after the update.
- **Writing riding modes 5-7** (debug build, standing still, in neutral, throttle closed).
- **Byte 88:** what the wheel-speed setting actually is (a circumference? a calibration index?) needs the bike.

### Which APK
- **`KawaNav-v0.8.apk`**: the app for everyday use.
- **`KawaNav-v0.8-debug.apk`**: the same app with the test tools (hidden cards: meter icons, bike data, notification capture) and the guarded writing of ride settings and shift lamp; tap the Settings title seven times. Both are signed with the same key, so one installs over the other and back, keeping rides, refuels, battery readings, the maintenance log and settings.

### Install / update
Open the APK on the phone (Android 13+). It updates v0.4 and later in place and keeps everything the earlier versions saved. It installs next to Darthbob's KawaNav, not over it: keep only one of them connected to the bike. Known limitations: [README](https://github.com/jackyes/kawa-nav/blob/v0.8/README.md#-known-limitations).
